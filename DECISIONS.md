# Decisions log

Deviations from `aequitas-implementation-handoff.md`, and choices made where the document is silent. Per Section 0: "Where this document conflicts with a library default, this document wins. Where it is silent, choose the boring, well-documented option and note the choice here."

## M0

- **Next.js 16.3.1 instead of the spec's "Next.js 15".** The existing scaffold (predating this handoff) is already on Next.js 16.3.1, App Router, current at time of writing. Downgrading a working, already-configured install for no functional benefit would be pure churn. Section 3's requirements (SSR UI + API in one codebase, strong a11y ecosystem) are equally met by 16.x.
- **TypeScript strict with `allowJs: true`, not a full JS→TS conversion in M0.** `tsconfig.json` sets `strict: true` for all new `.ts`/`.tsx` files, but the existing SQLite-backed domain code (`src/lib/db.js`, `workflow.js`, `ai.js`, `legalFramework.js`) is explicitly scheduled for replacement in M1 (Postgres/Prisma, event log, guards) per the handoff's own architecture. Converting throwaway code to TypeScript first would be wasted effort. New M0 deliverables (design tokens, i18n config) are written in TypeScript from the start.
- **next-intl scaffold built but not yet mounted at the live route root.** Message catalogs, i18n request config, and the parity/forbidden-terms CI checks are in place and passing. Restructuring the app under `/[locale]` and rewiring the existing pages through it is deferred to M2 ("role-scoped workspace" build-out), so the M0 scaffold doesn't redirect or break the currently-running SQLite demo mid-milestone. The i18n-parity and forbidden-terms checks run against the message catalogs directly, independent of routing.
- **CI implemented as a GitHub Actions workflow** (`.github/workflows/ci.yml`) — this repo already has a GitHub remote (`origin`), making Actions the boring, zero-new-infrastructure choice.

## M1

- **Prisma 7 connection config lives in `prisma.config.ts`, not `schema.prisma`'s `url` field.** Not a choice — Prisma 7 removed `datasource.url` from the schema file entirely (verified against current docs, not assumed from training data). `PrismaClient` construction correspondingly needs a driver adapter (`@prisma/adapter-pg`) rather than reading `DATABASE_URL` implicitly.
- **Standalone TS scripts (`verify:events`) run via `tsx`, not raw `node`.** Raw Node's ESM loader refuses relative *directory* imports (`ERR_UNSUPPORTED_DIR_IMPORT`) even when the directory has a valid `package.json` — that's bundler-only resolution behavior. The generated Prisma client (`src/generated/prisma/`) is exactly such a directory. `tsx` is the standard fix in the Prisma/Next.js ecosystem rather than hand-patching every import path.
- **`.env.local` loading for non-Next.js entrypoints is centralized in `src/lib/loadEnv.ts`**, imported as the *first* import in any file that also imports `src/lib/prisma`. ESM hoists all imports above inline code in the same file, so a same-file `dotenv.config()` call positioned after an `import { prisma } ...` line runs too late — `prisma.ts` reads `process.env.DATABASE_URL` at module-evaluation time, before the later `dotenv.config()` statement executes. Discovered when `verify:events` connected with an empty `DATABASE_URL`.
- **`verify:events` must run before `npm test` in CI (and in the local `ci` script), not after.** The Section 18 tamper test permanently corrupts one event row to prove `verify:events` catches it — by design, the append-only trigger makes that row impossible to clean up afterward. Running the two in the other order would make `verify:events` fail on every single CI run for a reason unrelated to the actual code under test.
- **`give_consent`'s Section-6 "DERIVED" outcome and the Section-7 consent lifecycle are implemented (`src/domain/consent.ts`, `src/domain/stateMachine.ts`'s `DERIVED` marker) but not yet wired into a mutation.** `runMutation`/`createCase` in `src/domain/mutate.ts` only implements `create_case` so far — evidence, positions, drafting, issuance, and consent mutations are M2-M4 work per Section 19. `src/domain/replay.ts`'s projection rebuild correspondingly only replays `CASE_CREATED`; every milestone that wires a new mutation must add its case to that reducer or `verify:events` will silently under-check the new event types.
- **`WEBAUTHN_RP_ID`/`WEBAUTHN_RP_NAME`/`WEBAUTHN_ORIGIN` are new env vars, not in Section 3's list.** A WebAuthn Relying Party cannot function without an RP ID and expected origin; defaults (`localhost` / `http://localhost:3417`) match local dev. **Testing gotcha confirmed live:** the sign-in page must be opened via `http://localhost:3417`, not `http://127.0.0.1:3417` — the browser correctly rejects `rp.id: "localhost"` against an IP-address origin ("127.0.0.1 is an invalid domain"), which is standard WebAuthn behavior, not a bug.
- **M1's self-registration allows a self-declared role among CONSUMER/RETAILER_HANDLER/CASE_MANAGER; ADMIN is blocked at the API level** (`src/app/api/auth/webauthn/register/route.ts`). Real invitation/provisioning policy for who can become a case manager is out of scope for M1 and listed as a gap here rather than silently assumed away — see Appendix B, "real access-control policy... must be locked down before real data."
- **`authenticate`'s options step returns a plain 404 for an unknown email**, not an enumeration-hardened generic response. Simpler to debug through M1-M3; logged here as a known hardening gap rather than claimed as production-ready.
- **The passkey ceremony is verified up to, but not including, a real hardware-backed completion.** Confirmed live in a real browser (not just unit tests): options generation returns valid `PublicKeyCredentialCreationOptionsJSON`/`RequestOptionsJSON` and sets a signed challenge cookie; the verify step correctly rejects malformed responses and missing/expired challenges (`verifyRegistrationResponse`/`verifyAuthenticationResponse` are genuinely invoked, not stubbed); the sign-in page reaches the real `navigator.credentials.create()` browser API and correctly blocks waiting on a platform authenticator. What's **not** verified: a full successful registration + authentication round trip with a real passkey, because neither a hardware authenticator nor a CDP virtual-authenticator (`WebAuthn.enable`) is available in this environment — the `browse` tool's CDP allowlist doesn't include the WebAuthn domain. This is a human task: complete one real registration + sign-in locally (Touch ID, Windows Hello, or a security key) before relying on this flow.

## M2

- **Bug found and fixed via live testing: `createCase`/`submitCase`/`openIntake` hardcoded a literal `actorRole` instead of passing the caller's real session role into `runMutation`.** This made the authorize-role step a no-op — any role could reach the guard-evaluation step regardless of what Section 6 actually permits for that trigger. `createCase`'s route had a redundant role check that happened to cover it; `submitCase`/`openIntake` had no such backstop and were genuinely unprotected at that layer (a downstream guard like `isCaseOwner` still caught the specific case I tested live, by coincidence of what that guard checks, not because the role gate worked). Found by minting a real session for a wrong-role test user and hitting the live endpoints — the response's rejection reason didn't match what the role check should have said. Fixed by threading `actorRole` through all three mutation input types from the caller's actual session; regression-tested in `test/integration/case-lifecycle.test.ts`, which calls the real mutation functions (not the generic `runMutation` primitive directly) so a future reintroduction of this exact bug would be caught. **Lesson applied going forward: every new mutation's role check gets a test that calls the mutation function itself, not just `runMutation` with an already-correct role hardcoded in the test.**
- **Case assignment is self-claim on `open_intake`, confirmed with the product owner** (Section 0 guardrail: Section 6 ambiguities are a stop-and-ask, not an improvise). Section 16's API surface defines no assignment endpoint, yet `open_intake`'s guard requires the case to already be assigned — nothing in the spec could satisfy that precondition. Resolution: a case manager claims an unassigned `OPEN` case by calling `open_intake` itself; the mutation sets `caseManagerId` to the acting manager in the same transaction as the state transition. Any `CASE_MANAGER` may claim any unassigned case — no queue/routing logic. `caseAssignedToManagerOrUnclaimed` (new guard) allows this only for `open_intake`; every other manager-gated trigger still uses the strict `caseAssignedToManager`, which requires prior assignment.
- **`open_intake` emits `CASE_ASSIGNED`, not the `coi.verified` that Section 6 row 3 literally names.** `coi.verified` does not exist anywhere in Section 8's canonical `EventType` catalogue (only `coi.declared` does) — doc drift between Section 6's prose and Section 8's own list, which states outright that it *is* the canonical list. `CASE_ASSIGNED` is in that catalogue, otherwise emitted by no Section 6 row, and is the semantically correct event for this build's self-claim resolution above.
- **Conflict-of-interest declaration is bundled into the `open_intake` request** (`{hasConflict, details?}` in the body) rather than a separate prior step — Section 16 defines no COI endpoint either. `coiDeclarationOnFile`'s guard now checks `{declared, hasConflict}` and blocks the transition outright when `hasConflict` is true (a case manager who declares a conflict cannot open intake on that case) — this is stricter than Section 6's literal "COI declaration on file" (which is silent on what happens if the declaration says yes), but consistent with why COI declarations exist at all (Section 14 lists them as compliance-relevant). A `CoiDeclaration` row is still written to the DB for the audit record; `request_draft`'s later `coiDeclarationOnFile` guard reads it back from there instead of from request input.
- **S3 upload and the ClamAV scan happen before `runMutation` is called in `submitEvidence`/`supersedeEvidence`, not inside `write()`'s transaction.** A Postgres transaction can't span an S3 PUT or clamd's raw-socket INSTREAM protocol. This means a DB failure after a successful upload can leave an orphaned object in the bucket with no matching `EvidenceItem` row. Accepted for M2's scope (evidence upload is genuinely two-phase: content-addressed storage write, then a DB row referencing it); a reconciliation job (list bucket keys under `live/`/`simulated/`, delete anything with no matching `storageKey`) is the real fix and is not built.
- **A file whose type can't be sniffed from its magic number (`fileTypeFromBuffer` returns `undefined`) is rejected outright (400), not stored with a guessed or client-declared MIME type.** Section 11 requires "MIME-sniffed server-side"; trusting the client's `Content-Type` for content that doesn't sniff would defeat the point of sniffing at all for a security-sensitive evidence-upload path. This means plain-text evidence (e.g. a `.txt` message export) with no distinguishing magic number is currently rejected — a known scope gap, not yet handled by a text/plain fallback.
- **Evidence-rejection notifications use the actor's real `User.locale`** (looked up at call time), following the same fix already applied to `submitCase`'s retailer-handler notification — a hardcoded locale was the M2 actor-role bug's exact failure shape and is guarded against here from the start rather than fixed after the fact.
- **Section 16's "RBAC failures return 404, not 403, for non-assigned cases" is now implemented via a new `MutationOutcome` step, `"not-found"`.** `runMutation`'s guard loop maps failures of a fixed set of case-access guards (`isCaseOwner`, `isCaseParty`, `caseAssignedToManager`, `caseAssignedToManagerOrUnclaimed`, `supersedesOwnItem`, `isConsentingParty`) to `"not-found"` instead of the generic `"guard"` step; every other guard (COI, evidence-count, version-sequencing) still maps to `"guard"`/409, since those failures mean the actor IS allowed to see the case and the action just isn't valid yet. `"Case not found"`/`"item not found"` pre-checks in `submitCase`/`openIntake`/`submitEvidence`/`supersedeEvidence` were also changed from `"authorize-state"` (409) to `"not-found"` (404) — that mapping was wrong before this fix, independent of the Section 16 requirement. **Known remaining gap:** the `authorize-state` (wrong from-state) check runs *before* any guard, so an actor who isn't a party to a case but who guesses a case ID currently gets a 409 ("cannot X from state Y") rather than a 404, if the case happens to be in a state the trigger can't fire from anyway — this still leaks that the case exists and (coarsely) what state it's in. Fixing this in general requires reordering the pipeline to check case-access before from-state, which is a bigger structural change than this milestone's scope; not done.
- **Live-verified finding, not a code change: this ClamAV build's EICAR heuristic only fires when the EICAR string starts at absolute byte 0 of the scanned stream.** The exact 68-byte EICAR file (`Eicar-Test-Signature`) and EICAR-followed-immediately-by-a-newline-at-offset-0 (`Eicar-Signature`) are both detected; EICAR appended after any prefix bytes (e.g. inside a real PNG's trailer, or with a single leading byte) is not. Confirmed via direct `scanBuffer()` calls with a byte-offset binary search, not assumed. This means "upload a file with EICAR embedded" is not a realistic way to test the REJECTED path end-to-end through the real MIME-sniffing HTTP route (a valid file's magic bytes necessarily precede any embedded EICAR text) — `test/integration/case-lifecycle.test.ts`'s REJECTED-path test therefore calls `submitEvidence()` directly with a pure-EICAR buffer and a manually supplied `mimeType`, deliberately bypassing the route's `fileTypeFromBuffer` sniff (that sniff is a separate, already-trusted library concern, not what this test is verifying).
- **`close_intake`'s "at least one evidence item per party" check counts only `scanStatus: "CLEAN"` items.** Section 11: a `PENDING`/`REJECTED` item is never visible to the other party or citable by the AI, so it shouldn't satisfy an evidence-coverage precondition either — a party who only ever submitted a since-rejected file has not, in the sense that matters, submitted evidence. In practice this build's scan pipeline never leaves an item `PENDING` (`scanBuffer` always runs to completion before the write), so the real distinction exercised is CLEAN vs. REJECTED. The override path (`overrideReason`) is unchanged and lets the assigned case manager close intake regardless of coverage, per Section 6's guard definition.
- **`submit_position` is a straightforward per-party append-and-version:** every call creates a new `PositionStatement` row at `MAX(version for that caseId+partyId) + 1`; there is no "supersede" concept for positions the way evidence has one; `oneCurrentVersionPerParty` (Section 6's named guard) is a descriptive invariant maintained by this versioning scheme, not a precondition that can fail — implemented as an always-`OK` guard function, same treatment `evidenceVisibilityRequiresCleanScan` already got in M1/M2. The "current" position for a party is simply the row with the highest version; no separate "is-current" flag was added since Section 5 doesn't define one.
- **`POST /api/cases/[caseId]/positions` resolves the position's `locale` from the request body if supplied, else the caller's `User.locale`** (looked up at call time, same pattern as the evidence-rejection notification fix above) — the session cookie payload (`src/lib/session.ts`) intentionally carries only `userId`/`globalRole`, not locale, so a stale/wrong locale can never get baked into a long-lived session token.
- **Live-verified end to end via curl against the running dev server, not just via automated tests:** `close-intake` correctly returns 403 for a non-manager, 404 for an unassigned/wrong manager, 409 for missing per-party evidence coverage, 200→`POSITIONS` once both parties have `CLEAN` evidence, and 409 again on a repeat call (wrong from-state); `positions` correctly returns 403 for a non-party (`CASE_MANAGER`), 400 for an empty body, and 200 with correct per-party version incrementing (consumer: v1 then v2; retailer: v1) confirmed directly against `PositionStatement` rows. `verifyCase`'s hash-chain check reports zero issues on the live case after these appends.

## M2 — `getAuthorityView` (Section 10)

- **`getAuthorityView(state, role, progress)` returns message *keys*, never literal strings.** Section 10's own sentence ("This is derived from the state machine + role, never hardcoded copy") is easy to misread as being only about avoiding ad hoc per-screen strings; Section 12 makes the stronger requirement explicit (every user-facing string goes through next-intl's fr-CA/en-CA catalogs, CI-enforced parity) — a "pure function" that returned English prose would violate that the moment it rendered. The function's third argument is `CaseProgress` (a handful of per-party completion booleans), not the full Prisma `Case` row Section 10's literal signature implies — the caller already knows the viewer's role relative to this case (that's resolved before this function is ever called, per Section 4's authorize-before-guard ordering), so passing the whole row would just be unused surface area.
- **Bug found and fixed by the test suite before this ever reached the UI: `triggerRolesFromState` cast a snake_case trigger name (`"open_intake"`) to the camelCase `AuthorityActionKey` type (`"openIntake"`) with `as`, which type-checks but performs no actual string transformation.** Every `has()` lookup against the resulting object therefore missed, silently: 32 of 68 hand-derived test cases failed on first run (every case where a role should have held real authority), each showing the same shape — `actionKeys` empty and `waitingOn` pointing at a role that, per the ground-truth table, should have had the authority itself. Fixed with an explicit `TRIGGER_TO_ACTION_KEY` map instead of a cast. Confirms the value of writing the full ground-truth table by hand (Section 6-style, independent of the implementation) rather than snapshot-testing whatever the function happened to already return.
- **Per-party progress is only precise for the two states M2 actually builds (`EVIDENCE_INTAKE`, `POSITIONS`).** From `DRAFTING` onward, "authority"/"next action" are derived from role-eligibility alone (no per-party consent-progress refinement — e.g. a consumer who already gave consent would still show `giveConsent` as an available action at `ISSUED`), because consent tracking doesn't exist until M4. Logged here rather than silently shipped as if it were precise; revisit once M4 builds real `ConsentRecord` reads.
- **ADMIN has no authority at any state** (Section 10's capability table lists no ADMIN row), consistent with the M1 decision to block ADMIN self-registration pending a real staff-access model — `getAuthorityView` always returns `actionKeys: []` for ADMIN, tested explicitly across all 10 states.
- **`withdraw`'s `ANY_EXCEPT_CLOSED` scope is taken literally, including the state it transitions *into* (`WITHDRAWN` itself is in `ALL_STATES.filter(s => s !== "CLOSED")`).** A consumer viewing an already-withdrawn case still shows `withdraw` as an available action — a harmless self-loop per Section 6's own table, not patched away, since silently overriding what the authoritative transition table says would be the same "hardcoded copy" mistake Section 10 warns against, just moved into logic instead of text.

## M2 — role-scoped workspace UI and `/[locale]` routing

- **Mounting `/[locale]` and building the real case workspace happened together, not as separate milestone tasks.** M0's own DECISIONS.md entry already anticipated this ("deferred to M2 ('role-scoped workspace' build-out)") — in practice it's a hard technical coupling, not just sequencing: `NextIntlClientProvider`/`setRequestLocale` only work once a request actually resolves to a locale segment, so there was no real "authority header" to build in isolation from the routing that makes a locale known.
- **The root layout (`src/app/layout.js`) keeps its `<html>`/`<body>` untouched; `src/app/[locale]/layout.tsx` is a nested layout with neither** — it only wraps children in `NextIntlClientProvider`. This is deliberate, not the more common next-intl pattern of moving `<html>`/`<body>` into the locale layout: doing that would require every route to live under `[locale]`, which would break the M0-era SQLite demo at `/` and `/auth/sign-in` (WebAuthn, M1) that Section 0 says not to disturb mid-milestone. Trade-off accepted and logged rather than silently shipped: `<html lang="en">` is static and does not reflect `fr-CA` pages — a real WCAG gap (3.1.1 Language of Page), out of scope for the M2 done-when criteria (Section 13's table doesn't list 3.1.1), to be fixed if/when the old demo is finally retired and everything moves under `[locale]`.
- **Bug found live, not by any automated test: `middleware.ts` was silently never invoked.** Next.js 16 deprecated the `middleware.ts` file convention and renamed it to `proxy.ts` (living at the same directory level as `app/` — here, `src/proxy.ts`, not the project root) — see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`, exactly the kind of breaking change `AGENTS.md` warns this Next.js version carries relative to training data. A `middleware.ts` at the project root type-checked, built, and produced zero errors or log output; it just never ran — an unprefixed `/cases/:id` 404'd instead of redirecting to `/fr-CA/cases/:id`. Caught only by manually curling the redirect path during live verification, not by `tsc` or the test suite (there is no unit test for proxy/middleware routing in this codebase). Fixed by moving the file to `src/proxy.ts`.
- **`next.config.mjs` never had the next-intl plugin wired in** (`createNextIntlPlugin("./src/i18n/request.ts")`), a second bug of the same shape as the proxy one: the M0 scaffold built `src/i18n/request.ts` but "not yet mounted at the live route root" apparently meant literally never connected to Next's config, not just unused. Surfaced as a 500 ("Couldn't find next-intl config file") the moment `[locale]/layout.tsx` first called `getMessages()`. Both this and the proxy rename required a full dev-server restart to take effect — Next.js does not hot-reload `next.config.mjs` or proxy/middleware registration.
- **Page-level access control for the case workspace: any party (consumer/retailer) OR any `CASE_MANAGER` (not just the assigned one) OR `ADMIN`; everyone else gets `notFound()`** (Section 16's RBAC-404 posture, applied to page routing, not just the API). An unclaimed manager must still be able to reach an `OPEN` case's page to call `open_intake` and self-claim it (see the M2 self-claim decision above) — restricting page access to only the *assigned* manager would make that impossible. `getAuthorityView` already correctly shows no `closeIntake`/etc. authority to a manager who isn't assigned once evidence intake has moved past claiming, and the mutation routes still independently enforce the real per-case guard (404) regardless of what the page renders — this page-level check is about who can *see* the case, not a second, weaker copy of the real authorization.
- **Live-verified with a real headless browser (Playwright via the globally-installed `/opt/playwright-node` package — not in this repo's `node_modules`), not just curl/RSC-payload inspection:** loaded the case workspace as consumer in both `fr-CA` and `en-CA` (full-page screenshots, correct role/authority/waiting-on text and evidence/position lists in both languages, zero `console.error`/`pageerror` events), submitted a position through the actual rendered `<textarea>`/button (not a scripted `fetch`) and confirmed the DOM updated post-`router.refresh()` with the new version appended, and loaded the same case as retailer and as two different case managers to confirm role-scoped rendering (case manager sees no evidence/position submission forms, no `REJECTED`-item visibility for evidence they didn't submit, and correctly sees `requestDraft` as their only available action once both positions are in).

## M2 — automated RBAC negative tests (`test/integration/rbac-http.test.ts`), Section 19 done-when

- **Route handlers cannot be unit-tested by direct import.** Confirmed empirically before writing this suite: calling an exported `GET`/`POST` function directly with a hand-built `Request` throws `` `cookies` was called outside a request scope `` from `next/headers`, because `requireSession()` depends on Next's request-scoped async storage, which only exists inside a real request lifecycle — Vitest never sets that up. This is why this suite is the first in the repo to spawn a real `next dev` server and drive it with `fetch()`, rather than importing the module under test — same "no mocks for what you're actually trying to prove" discipline this project already applies to MinIO/ClamAV/Postgres.
- **Scope is the RBAC status-code contract (401/403/404/409), on a representative route sample — not a second exhaustive replay of every guard.** Every guard combination is already covered at the domain-function level (`case-lifecycle.test.ts`, `mutate.test.ts`); what only an HTTP-level test can prove is that request parsing, `requireSession`, and `mutationFailureResponse`'s step→status mapping are wired correctly end to end.
- **Bug found live while writing the fixture, not a new gap: found the *already-documented* "authorize-state runs before guards" issue reproduce itself for real.** The first draft of the "unrelated consumer can't submit a position" test used a case still in `EVIDENCE_INTAKE` (submit_position's `from` is `["POSITIONS"]` only) and got a real `409` instead of the expected `404` — exactly the known, deliberately-deferred gap logged earlier in this file (task 33/34's RBAC-404 fix). Not a regression; the test itself was wrong for using a case in the wrong state to test the party guard. Fixed by adding a `freshPositionsCase()` fixture (closes intake with an override reason to skip evidence-coverage setup) so the test actually exercises the `isCaseParty` guard path it's named for.
- **Next.js 16 allows only one `next dev` process per project *directory*, regardless of port** — a second instance on a different port refuses to bind and prints "Another next dev server is already running," pointing at the first one's PID. This only collides with a developer's own already-running manual dev server (as happened once while building this suite); a CI runner or a clean local checkout never has one running, so it's a non-issue there. Not worked around in the test itself (detecting and reusing an arbitrary already-running server's port would be speculative complexity for a problem that doesn't exist in the suite's real execution context) — documented here instead, in case a future contributor hits the same collision locally.
- **The spawned server is killed via its process group (`process.kill(-pid, "SIGTERM")`), not just its own PID** — `next dev` spawns child workers, and killing only the parent would leave orphans; `detached: true` at spawn time is what makes the negative PID target the whole group. Verified no `next`/`next-server` processes remain after the suite exits.
- **17 tests, ~11s added to the full suite's runtime** (server spin-up dominates): 6 unauthenticated→401, 4 wrong-role→403, 5 right-role-wrong-party→404, 1 real business-conflict→409 (proving 409 and 404 aren't confused for each other), 1 sanity-check success path. All passing; full suite remains green at 434/434.

## M2 — remaining workspace UI (intake wizard, submit-case, open-intake) and the Playwright E2E suite

- **`createCase`/`submitCase`/`openIntake` had working API routes since M1/early M2, but no UI at all** — every case in this session up to this point was created via curl or direct domain-function calls. M2's own milestone description names "Intake wizard" and "case assignment" as UI deliverables, and the "M2 E2E segment passes" done-when criterion requires driving these through an actual browser, not the API directly — so building `src/app/[locale]/cases/new/` (intake wizard) and `SubmitCaseButton`/`OpenIntakeButton` (added to the case workspace, gated the same way as every other action button: `authority.actionKeys.includes(...)`) was necessary to have a real E2E flow to test, not optional polish.
- **The intake wizard bundles only `create_case`; submitting (`submit_case`) is a separate, explicit action on the resulting `DRAFT`-state workspace page**, not auto-chained. Two independently-authorized, independently-testable transitions stay two real UI actions — bundling them into one wizard click would mean the E2E suite (and any future user) never actually exercises `submit_case` through the UI on its own.
- **`@playwright/test` is now a real devDependency, with a project-level `playwright.config.ts` and `e2e/case-lifecycle.spec.ts`** — not another one-off verification script. `webServer.reuseExistingServer: !process.env.CI` means a developer's already-running `npm run dev` is reused with zero setup locally, while a fresh CI job (nothing running yet) gets one started automatically; this is the idiomatic Playwright pattern for exactly the "only one `next dev` per directory" constraint noted above, cleaner than the manual spawn/kill this file's own `rbac-http.test.ts` had to hand-roll (that one can't switch to `@playwright/test`'s webServer, since it isn't a Playwright suite — it's a vitest suite that happens to need a live server for a different reason: proving `requireSession`'s `cookies()` dependency actually works, not driving a browser).

## Deployment — Cloudflare Workers attempted, Railway shipped

- **Cloudflare Workers was attempted first and abandoned after extensive, genuine effort** (repo at github.com/martinlepage26-bit/aequitas, `wrangler.jsonc`/`open-next.config.ts`/`scripts/cf-build.sh` all still committed, inert). Real, verified fixes along the way: Next.js 16's Proxy defaults to the Node.js runtime with no way to opt back to Edge (`runtime` config throws in Proxy files) and OpenNext's Cloudflare adapter rejects Node-runtime middleware outright — `src/proxy.ts` had to be excluded from that build target entirely (loss: bare `/cases/:id` no longer auto-redirects there; every internal link already uses locale-prefixed hrefs, so this only affects hand-typed URLs). `better-sqlite3` (the M0-era legacy demo's DB) is a native addon Workers cannot execute regardless of size. A packaging bug quadrupled the 3.6MB Prisma WASM query compiler (~14MB of pure waste) via an ambiguous bare import resolving both `index.js`'s and `edge.js`'s dependency chains — fixed with an explicit `/edge` import (Cloudflare-build-only; it breaks under Vitest/Node). ~82MB of Prisma CLI/dev-tooling nothing at runtime imports (`@prisma/dev`'s embedded PGlite Postgres duplicated twice, Prisma Studio, native engine binaries for five database providers this Postgres-only app never touches) got pruned. **The hard stop:** the single Prisma WASM query-compiler file — required for any Postgres query through the driver-adapter architecture, not optional — is 3.59MB on its own, already exceeding Cloudflare's entire 3MB free-plan budget before counting anything else. Getting under it would mean replacing Prisma with raw `pg` queries, a real rewrite of the data layer, not a trim. The user chose not to upgrade to the $5/mo paid plan (10MB limit, which the app fits) and asked why Cloudflare was necessary at all — a fair question, since Workers' isolate runtime (no native binaries, hard bundle caps, WASM-only for compiled deps) is fundamentally in tension with a batteries-included ORM, a friction Vercel/Railway/Fly (plain Node processes) don't have.
- **Railway was chosen instead** — a plain long-running Node process (`next build` / `next start`), no bundle-size limits, no WASM/native-binary restrictions, no adapter surgery. `src/lib/storage.ts` gained a third backend (local filesystem, `STORAGE_LOCAL_DIR`, checked before R2/S3) specifically for this: a plain server with a persistent volume needs no external object-storage account at all, unlike Workers' stateless-isolate model where a native R2 binding was the only credential-free option.
- **The generated Prisma client (`src/generated/prisma/`, gitignored — regenerated from `prisma/schema.prisma`) was never being regenerated in Railway's build**, since `npm run build` is `next build` only. Fixed with a standard `postinstall: "prisma generate"` hook. That hook itself then failed because `prisma.config.ts`'s `env("DATABASE_URL")` validates the variable eagerly even for `generate` (which doesn't need a live connection) — resolved by setting `DATABASE_URL` as a Railway variable, which was needed anyway.
- **Database: Supabase Postgres (session pooler, port 5432), not Railway's own Postgres plugin** — the user supplied a Supabase project already. Supabase's *direct* connection is IPv6-only by default and this sandbox has no IPv6 egress; the *transaction* pooler (port 6543) hung indefinitely on `prisma migrate deploy` (PgBouncer transaction-mode releases the connection between statements, breaking Prisma's session-scoped advisory lock) — the *session* pooler (port 5432, same Supavisor pooler, session-scoped) was the one that actually worked for migrations, and is what's configured for the app's own runtime `DATABASE_URL` too.
- **ClamAV is a real, second Railway service in the same project** (`clamav/clamav:stable`, the same image `docker-compose.yml` already uses locally), reachable over Railway's private network at `clamav.railway.internal:3310` — not a documented gap this time, since Railway (unlike Workers) can run an arbitrary long-lived TCP daemon. `submitEvidence`/`supersedeEvidence`'s `safeScan()` wrapper (added for the Cloudflare attempt, where this WAS going to be a permanent gap) turned out to matter for Railway too: it caught the brief window before the ClamAV service/variables were wired up, returning an honest "scanning is unavailable" guard failure instead of an unhandled crash — verified live before ClamAV was connected, then verified working for real afterward.
- **`ANTHROPIC_API_KEY` remains unconfigured** — no real Anthropic API key was available in this environment. Same honest, documented gap as every prior milestone; `request_draft` correctly returns its 502 "AI recommendation drafting is unavailable" on the live deployment, verified directly.
- **A Turbopack build warning, not fixed for Cloudflare (moot there) but fixed for Railway (the real deploy target): `STORAGE_LOCAL_DIR`-based paths in `storage.ts` are inherently runtime-only (a volume mount path from an env var), which Turbopack's static file-tracer can't resolve** — without an ignore hint it traces (and bundles) the entire project into the server output. Fixed with `/*turbopackIgnore: true*/` on both `join()` calls, per Next's own suggested remediation.
- **Live-verified against the deployed production app on Railway (hostname intentionally not recorded here), not a local server** — session cookies minted directly against the same Supabase database using the app's real `SESSION_SECRET` (set as a Railway variable), then the complete lifecycle driven through the live HTTP API exactly as the local M4/M5 verification was: a real `P2P_MARKETPLACE` case from creation through real evidence upload (real ClamAV scan, real Railway-volume storage), positions, the honest AI-unavailable 502, a hand-seeded recommendation, issuance, both parties consenting (→ `RESOLVED_CONSENT`), closure (real export generation), and a downloaded, unzipped, valid 3-file export bundle. A real headless-browser screenshot of the live, closed workspace (zero console errors) confirmed the category-correct "buyer" role label and the full 16-event timeline render correctly in production.
- **Live-verified end to end, not just unit-tested:** created a real `TENANCY`-category case via the actual running app (curl, then again through a real headless-browser form fill/submit — `#respondent-email` → `#category` select → real button click), confirmed the workspace correctly renders "Votre rôle : locataire" (fr-CA) and "Your role: tenant" (en-CA) for the complainant on that case, and confirmed a case created with no category specified still renders "consommateur ou consommatrice" (RETAIL default, unchanged pre-pivot behavior). Full suite green after the pivot: 456/456 unit+integration tests, 2/2 Playwright E2E (both locales), lint, typecheck, `check:i18n-parity`, `check:forbidden-terms`, and `next build` all clean. (Two transient failures during the *first* post-pivot test run — `rbac-http.test.ts`'s spawned dev server refusing to bind because a leftover manual `next dev` from earlier in this session was already holding this project's single-instance lock, and one `verify-events-tamper.test.ts` run losing a race against parallel test-file execution on the shared local Postgres container — were confirmed environmental, not regressions, by direct reproduction in isolation before rerunning the full suite clean.)

## Post-M5 — respondent invite-by-email (real gap found live in production)

- **`POST /api/cases` previously required the respondent to already be a registered `RESPONDENT` user** — a complainant could only open a case against someone who had already signed up and picked that role first, with no way to name a new counterparty. Found live, not by a test: creating a case against `ml@pharos-ai.ca` (a real but not-yet-`RESPONDENT` account) 400'd with "No respondent exists with that email." Fixed in the route (`src/app/api/cases/route.ts`), not in `createCase()` itself — deliberately, to avoid touching `CreateCaseInput`'s `respondentId: string` contract and the several integration tests that call `createCase()` directly with an already-resolved id. The route now does the existing-user lookup it already did, but only *rejects* when an email is already registered under a *different* role (a complainant can't silently repurpose someone else's account); otherwise it `upsert`s a placeholder `User` (`globalRole: "RESPONDENT"`, no credentials, from a new required `respondentDisplayName` field) before calling `createCase()` exactly as before.
- **This composes for free with the existing registration flow** — `src/app/api/auth/webauthn/register/route.ts`'s verify step already does `existing ?? create` keyed on email, so a respondent who later self-registers with the same email attaches their passkey to the placeholder row instead of erroring or duplicating it. No change was needed there.
- **No real email is sent.** `EMAIL_FROM` is declared in `.env.example` but nothing in this codebase ever sends mail — `Notification` rows are in-app DB records only. The new `respondentNameHint` i18n string says this plainly: the complainant must tell the respondent, out of band, to sign in with the exact email used. A real invite email is the natural follow-up once an email provider is actually wired up; not built here, not silently implied to exist.
- **Left as a known, minor gap, not engineered around:** the pre-transaction `findUnique` + `upsert` in the route has a narrow theoretical race (two complainants inviting the same brand-new email at the same instant) that a fully transactional resolve-inside-`createCase` would close. Not worth widening `CreateCaseInput`'s contract and rewriting its test suite for a race this app's real usage pattern won't hit; logged here rather than left for someone to discover later.
