# Case agent (2026-11-06)

Status: **off by default; tested on synthetic data with a stub model only.** No live model has been evaluated. Do not enable it for real cases before the decisions at the end of this page are made.

## Routine path it handles without a case manager

All workflow decisions are deterministic code under the program's configured rules (`src/domain/caseAgent/config.ts`). The model drafts a staff summary, picks a remedy from a closed list, and supplies staff-only, evidence-linked reasons for that proposal. Each party receives fixed wording; neither the rationale nor the other party's evidence links are shown to them. Every step below is a separate scheduled pass (`npm run agent:run`); each pass is idempotent and re-checks the case row under lock.

1. **Take the case.** A submitted `OPEN` case with no assigned manager is taken by the agent (`agent_open_intake`) only if it is `RETAIL` and its amount at stake is present and within the program limit. Anything else stays in the normal case-manager queue untouched. Both parties receive a bilingual notice by email and on the case page: the agent handles routine steps, proposals are not binding, are not legal advice and do not judge truthfulness. Either party can ask for a person before closure; the complainant can end participation, and the respondent can do so only if the program enables it.
2. **Invite the respondent.** The agent creates the existing respondent invitation and an encrypted delivery payload in one transaction (`PARTY_NOTIFIED` event, same invitation tables and email as the complainant-initiated path). It tries delivery immediately. If Resend is temporarily unavailable, the message stays queued for the scheduled mail worker; a permanent rejection, exhausted retry budget, or respondent who does not join within the response period sends the case to a person.
3. **Collect evidence.** Parties upload through the existing evidence form: MIME allowlist, size limits, ClamAV scan, hash recorded. Each party must mark their own evidence intake complete; a new submission clears that party's mark, and a case-detail change clears both. The agent closes intake (`agent_close_intake`) only after both current marks and at least one clean item from each party, then queues a bilingual request for each party to submit or update their position. It can close as soon as both are ready. At the configured maximum period, an incomplete submission or a party who has not marked complete goes to a person; silence never counts as readiness. A pending scan makes it wait until that period ends, then goes to a person. A rejected file goes to a person immediately.
4. **Collect positions and ask about provider processing.** Parties submit positions as usual. A missing position after the response period goes to a person. Once both positions are in, each party sees the configured provider and model, the exact notice in their selected language, and a separate acceptance button. The service does not extract evidence files or send positions or extracted file text to the model provider until both parties accept the current provider, prompt version, and bilingual notice. Each choice is an append-only `AGENT_PROCESSING_ACCEPTED` event that records its author, exact notice text, locale, provider identity, prompt version, and notice hash; parties cannot see the other party's choice. A provider, model, prompt, or notice change makes earlier choices no longer valid. Either party can request a person instead; if both choices are not recorded by the response deadline, the case is handed to staff.
5. **Read the evidence and propose.** Only after both processing choices match, and before any model call, the agent:
   - downloads every current clean item and checks its stored size and SHA-256
   - extracts text (see below)
   - stops for a person if anything is unreadable, partial or over the limits

   The model returns a staff-only summary and reasoning as separate claims, a structured proposal (`refund_full`, `refund_partial`, `store_credit`, `replacement` or `repair`, plus an amount where one applies), atomic proposal-basis claims, citations with exact excerpts, and the evidence each party's outcome relies on. Every summary, reasoning, and proposal-basis claim must point to one or more citation IDs; the stored record preserves those claim-to-quote links. Deterministic checks then require:
   - a strict schema with no extra fields
   - every excerpt appearing exactly once in the cited file's extraction
   - every summary, reasoning, and proposal-basis claim pointing to an existing exact-quote citation, with no unlinked citation
   - each party's outcome pointing only to that party's own evidence
   - an amount that is needed by the remedy and not above the amount at stake
   - no verdict, credibility, score, legal-advice, binding or pressuring language in any model text

   A failed check goes to a person; nothing is partially written.
6. **Issue.** One locked write (`agent_issue`) stores the recommendation, both party outcomes, per-outcome citation pointers and notifications. If any material the model saw changed during the call, the result is discarded as stale and redone on the next pass.
7. **Answers.** Parties consent or decline through the existing consent flow, which binds each answer to the outcome version. The promised autonomous routine path uses `AEQUITAS_CASE_AGENT_CONSENT_ONLY_RESOLUTION=true`: both parties must consent to the current outcome version, and no independent approver signs that routine case. If program policy requires an approver, setting `false` keeps the sign-off gate. Any handoff restores independent approval. An unanswered proposal after the response period goes to a person.
8. **Close.** After both parties consent, or after either party ends participation under the configured rules, the agent generates the sealed export and closes the case (`agent_close`). A decline goes to a person; the agent never closes a declined case.

## Handoffs to a person

The agent records `AGENT_ESCALATED` with a reason and notifies the assigned case manager. If no manager is assigned, it notifies every case-manager account with a passkey (the program's queue). An unassigned escalated case appears in every case manager's list; one manager takes it by declaring no conflict of interest (`POST /api/cases/[id]/claim`). From then on, normal human rules apply, including approver sign-off. Before a provider call, each scheduled pass re-reads the handoff marker and case material; a request for a person or a material change observed during extraction prevents that call. If a request races with or follows the final pre-call check, the provider request may still start or finish, but its result is discarded and cannot be issued.

If a party withdraws after an unassigned case has been handed to the queue, a conflict-free manager can still claim the escalated case, generate its sealed export and close it. The agent remains stopped after the handoff.

Reasons:

| Area | Reasons |
|---|---|
| Party choice | `party_request` (either party, any time before closure), `processing_choice_timeout` (both did not accept the provider disclosure before the deadline), `declined` |
| Invitation and timing | `invitation_failed`, `respondent_no_response`, `submission_missing`, `intake_incomplete`, `evidence_scan_pending`, `no_answer` |
| Scope | `out_of_scope_category`, `out_of_scope_amount` |
| Evidence | `evidence_rejected`, `evidence_inadequate`, `evidence_extraction_failed`, `evidence_limit_exceeded` |
| Process | `contestation_open` |
| Program configuration | `program_rules_incomplete` |
| Model and capacity | `model_unavailable`, `model_failed`, `model_requested_review` (including unresolved material-fact conflicts), `model_output_rejected`, `daily_model_call_limit_reached`, `model_budget_unavailable` |

## Evidence the agent actually reads

The agent reuses the existing pipeline in `src/lib/evidenceText.ts`:

| Format | Method | Notes |
|---|---|---|
| `text/plain` | UTF-8 decode | |
| PDF | `pdftotext` for text-only pages; `pdfimages` detects pages with embedded images, which are rendered with `pdftoppm` and OCRed with `tesseract` as a whole page | Up to 20 pages. A longer file is "partial" and goes to a person. The page number is recorded with each citation. OCR may misread text. |
| PNG, JPEG, TIFF, WebP | `tesseract` OCR | Languages from `AEQUITAS_OCR_LANGUAGES`. OCR text is cited as extracted, not corrected. Static rasters only; multi-page TIFF and animated PNG/WebP go to staff. |

- **Limits:** 25 MiB per file, 12 MP and 12,000 pixels per axis for direct image OCR, 12,000 characters per source, 12 files and 60,000 characters per case. Malformed image headers, animated PNG/WebP, multi-page or BigTIFF files and any other unreadable, partial or over-limit extraction go to a person.
- **Not read:** any page that remains empty after OCR, other formats (unsupported), and any truncated extraction. Each of these goes to a person. A filename or description is never treated as proof. When a page contains an embedded image, the selectable text layer and rendered OCR are retained together; OCR does not discard text already extracted from the PDF.
- **Citations:** each records a stable response citation ID, evidence id, start and end character offsets, the source-file SHA-256, the extracted-text SHA-256, the extraction method and, for PDFs, the page. Summary, reasoning, and proposal-basis claims reference these IDs. A party opening a cited outcome excerpt gets it re-extracted and re-verified against both hashes. Citation digests are bound to the issuance event and checked by `verifyCase`.
- **What the links prove:** they make it possible to trace each staff summary, reasoning, or proposal-basis claim to an exact excerpt in a hash-verified extraction. They do not prove that the excerpt semantically supports the claim, or that the document is authentic, accurate or relevant. Staff review and live-model evaluation are still required.

## Privacy and party choice

- **Fixed party text.** No model-written sentence reaches a party. Each party reads fixed French or English wording generated from the structured proposal (`src/domain/caseAgent/proposal.ts`), plus excerpts from their own evidence only. The summary, reasoning and citation notes stay with staff. This replaces the earlier six-word overlap check, which could not prove that a paraphrase leaked nothing.
- **Provider processing choice.** The per-case agent panel shows the configured provider and model and the program-supplied notice in English or French. The application appends a fixed bilingual explanation that a provider request starting or in progress may still be sent or finish processing information already sent, and that an in-flight result is discarded if the request for a person is recorded before proposal issuance. The complete displayed text is hashed and stored with each party's choice. The case agent waits for separate choices from both parties before extracting evidence files or sending positions or extracted evidence text to that provider. A changed provider, model, prompt version, or notice invalidates prior choices. Missing configuration keeps the agent off; a party can ask for a person instead. The added wording still requires program and counsel review before real case data is used.
- **Isolation rules unchanged.** The existing submission-visibility contract still applies: parties never see the other side's submissions, outcome or request for a person.
- **Ending participation.** Either party can request a person until closure. The complainant can always end participation. The respondent can on agent-managed cases when the program setting `AEQUITAS_CASE_AGENT_RESPONDENT_MAY_WITHDRAW` is `true`; there is no default. Human-managed cases keep the existing complainant-only withdrawal rule.

## Permissions

- **Account.** The agent acts as one `CASE_AGENT` service account (`npm run agent:provision`). No session can be issued for that role and it has no passkey.
- **State machine.** It holds exactly `agent_open_intake`, `agent_close_intake`, `agent_issue` and `agent_close`, each guarded by `agentMayAct` (opted in, not escalated, actor is the agent). A unit test asserts it holds nothing else.
- **No case access.** `caseReadAccess` gives it nothing, so it cannot use any route.
- **What it cannot do.** Tests show it cannot consent, decline, approve, write outcomes as a manager, request a person, or administer users.
- **Prompt boundary.** The model receives the program's rules in the provider's system/developer instruction channel and the party submissions and evidence in a separate user-data message. Party content is still untrusted model input; role separation strengthens the boundary but does not prove a model will resist every instruction embedded in evidence. The deterministic output checks and human escalation remain required.
- **Audit.** Every agent write appends hash-chained events attributed to the agent, with the model id, the prompt version (`case-agent-2026-11-07.1`) and a digest of the material it saw. Summary, reasoning, and proposal-basis claims link to verified extracted excerpts for staff review and are removed from party views. These exact links make review traceable; they do not prove that an excerpt semantically supports a claim.

If program rules are missing or invalid, the agent takes no new case and hands active agent-managed cases back to staff. New cases also wait in the normal queue until an approved provider is configured. Email delivery must be configured for the respondent invitation; otherwise the case goes to a person.

Both manager enrollment and automatic queue enrollment write a versioned policy snapshot into the hash-chained `AGENT_ENROLLED` event. Active cases keep the enrolled intake and response periods, respondent-withdrawal choice, and consent-resolution rule when deployment settings change. The live amount ceiling can tighten eligibility before a proposal and send a case to staff, but cannot expand an enrolled case's amount limit. The daily model-call ceiling, global enablement, and exact provider-processing disclosure remain live operational controls. An active case with a missing, malformed, or unknown policy snapshot is handed to staff; the agent never reconstructs old party terms from current settings.

The daily call ceiling is enforced with an atomic PostgreSQL counter shared by all scheduler workers and resets at 00:00 UTC. The counter stores only one aggregate row per UTC day, with no case or party identifiers. It limits call volume, not dollars: model prices and token use vary, so operators must also configure provider-side spend alerts or limits. When capacity is exhausted, new open cases stay in the ordinary case-manager queue; cases already managed by the agent are handed back at the proposal step. If the usage store cannot be checked, new cases stay in the ordinary queue, active cases are handed to staff, and the agent makes no model request. A missing or invalid processing notice is part of incomplete program configuration; active agent-managed cases return to staff rather than proceeding without the party choices.

**Runtime model.** The agent uses the existing `TextCompletion` interface: Gemini Developer API (`GEMINI_API_KEY`, optional `GEMINI_MODEL`), Google Cloud Vertex AI (`AEQUITAS_VERTEX_PROJECT_ID` and ADC), or Cloudflare Workers AI (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, optional `AEQUITAS_WORKERS_AI_MODEL`), selected by `AEQUITAS_PIPELINE_PROVIDER`. The current Vertex adapter is limited to `gemini-3.5-flash` in `northamerica-northeast1` (Montréal). Anthropic and OpenAI are refused on this path. Calls are billed to the deployment's own provider account, not to Claude Code Cloud credits. Current provider data terms, project settings and transfer conditions still require program and counsel review.

For Workers AI, the case agent supplies its output schema as one required function call, with a 16,000-token request ceiling. Cloudflare documents the OpenAI-compatible `/v1/chat/completions` endpoint; its Gemma 4 model page lists function calling and `tool_choice: required`, which matches the adapter's request shape. The application still parses the result through the same strict Zod schema and checks every citation and program rule; a missing, malformed or unexpected tool call is handed to a person. Function calling improves output shape but does not establish factual accuracy, neutrality or French quality. This adapter is covered by mocked tests only: the official contract documentation supports the request format, but an authenticated call against the selected account and the live response shape still need the gated synthetic evaluation ([Cloudflare OpenAI-compatible endpoints](https://developers.cloudflare.com/workers-ai/configuration/open-ai-compatibility/), [Cloudflare function calling](https://developers.cloudflare.com/workers-ai/features/function-calling/traditional/), [Gemma 4 model details](https://developers.cloudflare.com/ai/models/%40cf/google/gemma-4-26b-a4b-it/), [JSON Mode model list](https://developers.cloudflare.com/workers-ai/features/json-mode/), [Workers AI model input limits](https://developers.cloudflare.com/api/resources/ai/methods/run/)).

Unsupported JSON Schema keywords such as regex patterns, string-length limits and exclusive numeric bounds are omitted from the provider request; the application's strict Zod validation still enforces them after generation and hands invalid output to a person. This request is covered by a mocked test only. **Scheduling.** `npm run agent:run` is one bounded pass. The CT920 `scheduled` Compose profile runs it every 10 minutes and notification retries every 15 minutes. `deploy/ct920/deploy.sh` stops an existing worker before migrations and starts the profile only after the app reports the new release SHA healthy; direct default-profile `docker compose up` does not include it. Confirm operations with `npm run agent:status`; the case agent itself remains off until its complete program, provider and evaluation settings are present. Set `AEQUITAS_EMAIL_OUTBOX_ENCRYPTION_KEY` to the same stable value in the app and scheduler environment (at least 32 bytes); the worker needs it to decrypt queued invitation/recovery messages. It receives no `SESSION_SECRET` or WebAuthn secrets. Each case is leased before a pass, revisited no sooner than 10 minutes later, and recovered after a 30-minute crashed-worker lease. A missing provider prevents new cases from being taken; already agent-managed cases can still close after consent or be handed back.

`npm run agent:status` also reports aggregate scheduler heartbeats for both scheduled operations and a sanitized reason when provider configuration is blocked (for example, a missing or mismatched terms-review identity). It marks a worker never observed, running, healthy, overdue, stalled, failed or interrupted; the rows contain only operation names, schedule intervals, outcomes, exit codes and timestamps, never case identifiers, party data, evidence or provider errors.

**Operator status.** `npm run agent:status` prints aggregate readiness, case-state, escalation, lease, notification, UTC-day model-call usage and scheduler heartbeat data; it omits case IDs, party details, evidence, addresses, provider errors and secrets. A recent healthy heartbeat shows the operation completed within two configured intervals; it cannot prove that the scheduler process did not stop immediately after its last heartbeat. Check the scheduled-profile logs for exact operational errors and the provider account for usage and billed cost.

## Evaluation

`npm run agent:evaluate -- --stub` exercises the harness offline. `--live` runs six synthetic fixtures against the configured provider, with at most one model call per fixture, and refuses to start unless `AEQUITAS_CASE_AGENT_EVAL_APPROVED=true`, which the operator sets after confirming the provider's data terms and spending limit. It also enforces the provider terms and Gemini billing gates above. It writes only to the `_test` database and a temporary local evidence directory, and suppresses outbound email. The evaluator can run before the quality-review attestation exists; the production case-agent resolver cannot. It emits an approval identity only when every automated fixture check passes.

After provider approval, add `--review-report=/tmp/aequitas-case-agent-review.json` to write a separate local review artifact. It contains the stored summary, reasoning, proposal, proposal-basis claims, claim-to-citation links, hash-verified cited excerpts, fixed party outcomes, a bounded sanitized `needs_human` request when valid JSON provides one, automated mechanics results, and blank human-review fields. It omits prompts, complete evidence files, case and party IDs, and credentials; common email, North American phone, and Canadian postal-code patterns are redacted, but redaction is not comprehensive. A separate boolean records whether the seeded phone marker appeared in the complainant-facing outcome before redaction. Keep the report local and review it with the owner, operator, counsel, and a Québec French reader as appropriate. Automated checks do not grade factual support, neutrality, legal suitability, or language quality; the report is not an approval or readiness decision.

After the live report has passed its automated checks and the appropriate humans have reviewed the generated text beside its cited excerpts, mark every checklist field `pass` only when that criterion actually passes, add any needed reviewer notes, and change the report's `status` to `human_review_complete`. Then run:

```sh
npm run agent:approve-evaluation -- --review-report=/tmp/aequitas-case-agent-review.json --confirm-human-review
```

The validator refuses stub reports, failed or incomplete fixtures, missing/unverified citations, party-isolation failures, a detected or unverified synthetic contact leak, escalated fixtures with recommendations, incomplete checklists, stale provider/account/model/prompt/evaluation-protocol identities, and reports that have not been marked `human_review_complete`. It prints the exact `AEQUITAS_CASE_AGENT_EVALUATION_REVIEWED_FOR=...` assignment for the operator to configure; it does not edit environment files or call a provider. `--confirm-human-review` is an operator assertion: the tool validates the supplied JSON but cannot prove who reviewed it, whether the judgments are sincere, or whether counsel approved the program. Bump `AGENT_PROMPT_VERSION` when the prompt or runtime output checks materially change. ## Known limits

- **Test coverage:**
  - A stub stands in for the respondent's passkey enrolment.
  - Scanning in the routine integration tests is seeded; the browser test uploads through the real scanner in CI.
  - Page-number citation is verified end to end for searchable and OCR-extracted scanned multi-page PDFs.
- **Heuristic checks.** The deny list catches forbidden phrasing in staff-only model text; it cannot prove that text is accurate or neutral.
- **Escalation behaviour:**
  - Any model failure escalates at once; there is no retry budget.
  - Invitation and account-recovery messages use encrypted outbox fields on their token records. The exact provider payload (including recipient and one-time link) is AES-GCM encrypted with an HKDF-derived key from the distinct `AEQUITAS_EMAIL_OUTBOX_ENCRYPTION_KEY`, and authenticated to the message kind and record ID. It is cleared after provider acceptance, revocation, use, or expiration cleanup. The scheduled mail worker retries uncertain delivery no sooner than 15 minutes after the previous attempt, at most eight attempts, using the same payload and `invitation/{id}` or `recovery/{id}` idempotency key. Resend documents a 24-hour key-retention window ([idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys)).
  - A permanently rejected or undecryptable invitation is not re-sent; an agent-managed case returns to staff. Definite recovery-email rejection revokes the recovery token. A pending recovery link expires after 30 minutes; the generic endpoint response does not reveal whether an account exists. Changing `AEQUITAS_EMAIL_OUTBOX_ENCRYPTION_KEY` makes queued payloads undecryptable and fails delivery closed, so the user must obtain a new invitation or recovery link. The bounded outbox does not replace real-host delivery checks or establish provider-side email retention.
- **Scope:**
  - One program per deployment. Roles are global, so this is not multi-organization software.
  - Two parties only. No retention or deletion service.
